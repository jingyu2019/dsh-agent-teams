### 2.2 F1（high，阻断发布）：devDependency 与 recommendedHost 脱节

- `package.json:241`：`"@deepseek-ai/dsh": "0.2.1-rc.5"`。
- `compatibility.json:3`：`"recommendedHost": "0.2.2-rc.1"`。
- `.github/workflows/publish.yml:82`：当 `NPM_DIST_TAG === 'latest'` 时
  `assert.equal(pkg.devDependencies['@deepseek-ai/dsh'], policy.recommendedHost)`。
- 现场模拟判定：该断言 **FAIL**。即：矩阵前移后，任何 `latest` 发布都会在发布闸门被拒。
- 影响：t9 只改了 `compatibility.json`，未同步 devDependency（`package.json` 在 t2 范围内只加了 verify 脚本条目）。`pnpm-lock.yaml` 仍锁 0.2.1-rc.5 cohort，构建可用，但与 recommended 不一致。
- 修复建议（不在 t4 范围）：把 devDependency 与 lockfile 升到 0.2.2-rc.1，或明确把发布闸门改为允许 devDep 与 recommendedHost 不同并给出理由。

### 2.3 F2（high，阻断 0.2.2 CI）：冷恢复场景脚本与 0.2.2 headless 组合不兼容

复现（真实 0.2.2-rc.1 运行时，隔离 DSH_HOME，`node scripts/harness-runtime-scenarios.mjs` 的同一调用契约）：

- warm `lifecycle`：**10/10 断言通过**（requests 16，memberRequests 6）。
- 随后官方脚本自动追加冷恢复：`scripts/harness-runtime-scenarios.mjs:225` 把 profile patch 追加为
  `- id: headless-startup disabled: true` + `- id: headless-runner disabled: true` + 插入 `fixture-resume.mjs`，`:227` 启动 `dsh --profile headless`。
- 冷运行结果：`exit0=true`、`driverCompleted=true`（stdout `COLD_RESTORE_DRIVER_DONE`），但
  `memberToolsRestricted=false`、`sameMemberRestored=false`、`routeRestored=false`、`reasoningRestored=false`；
  `cold-trace.jsonl` 只有 4 条事件，**没有 `cold-member-completed`**。
- 冷 stderr：`dsh: warning: 21 entries did not activate`，根链为
  `working-directory … waiting for service: fs`
  → `fs-sandbox … waiting for service: sandboxPolicy`
  → `sandbox-policy … waiting for service: headlessStartup`
  → `subagent … waiting for service: workingDirectory`
  → `agent-teams … waiting for service: subagents`。

根因（对比两代产物）：

| 版本 | `@deepseek-ai/dsh-headless/cordis.patch.yml` |
| --- | --- |
| 0.2.1-rc.5 | 全文件 **0 处** `sandbox-policy`；冷场景禁用 `headless-startup` 不牵连其它服务 |
| 0.2.2-rc.1 | `:28-29` 新增 `- id: sandbox-policy` + `inject: [headlessStartup]`（CLI grants 覆盖） |

因此 0.2.2 上禁用 `headless-startup` 会让 `sandbox-policy` 永远 pending，级联冻结 `fs / workingDirectory / subagents`，`agent-teams` 无法激活。**这是场景脚本的宿主假设过期，不是插件回归。**

反证（同一 0.2.2 运行时，只改冷启动组合）：保留 `headless-startup`，仅禁用 `headless-runner`，其余不变，重跑同一冷恢复：

- `COLD_RESTORE_DRIVER_DONE`，stderr 为空（无未激活条目）；
- `cold-member-completed` 出现，`sessionId=c1eff8af-ed84-4333-98f9-91bf8478e101`（与 warm 的 worker 一致）、`model=fixture-model`、`reasoningEffort=high`；
- 成员请求工具集收敛（不含 `agent_teams_create`，含 `agent_teams_claim_task`）。
- 即冷恢复 5 项断言全部可满足，**插件侧冷恢复在 0.2.2 上正常**。

影响：`.github/workflows/verify.yml:155-159` 对矩阵每个 host（含 0.2.2-rc.1 的 ubuntu+windows）跑 `harness-runtime-verify.mjs`，该脚本默认包含 `lifecycle` 场景（`scripts/harness-runtime-verify.mjs:162`），冷恢复必然执行 → **0.2.2 矩阵 CI 会红**，直到 `scripts/harness-runtime-scenarios.mjs:225` 调整为“只禁用 headless-runner，或在禁用 startup 时同时覆盖 sandbox-policy 的 inject”。
