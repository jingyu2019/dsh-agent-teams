## 1. 0.2.2 支持范围：能承诺什么

支持的判据是**运行时能力**，不是版本号比较、也不是函数 arity 嗅探：

```ts
const controller = agent.model
if (typeof controller?.select === 'function') { /* 0.2.2+ 路径 */ }
```

落点在 `src/harness-compat.ts` 的 `memberSelectionChannel` / `installMemberSelection`（`MemberSelectionChannel` 暴露 `route()` / `apply()` / `redirectsInStepRetry`）。两代差异被显式建模而不是隐式吞掉：

| 行为 | ≤0.2.1（ref 拥有路由） | 0.2.2+（Agent 拥有路由） |
| --- | --- | --- |
| 选择通道 | `installModelSelection(agentCtx, ref)` + 写 ref | `installModelSelection(agentCtx)` + `agent.model.select(route)` |
| system-prompt 变量注入 | 插件经 assemble 钩子注入 provider/model | 宿主自己做（agent-loop 提供变量），插件不再注入 |
| `agent/request` 重写 | 有，可改在途请求路由 | 无；改写路由会被宿主抛 `use agent.model.select() before step preparation` |
| 在途重试改路由 | 可表达 | **不可表达**：step preparation 一次性固定本步路由，`select()` 只影响下一个 step |
| 成员 fallback 消费判定 | 返回 `{ kind: 'retry' }` | 返回 `undefined`（不再声称 in-step retry），并把 fallback 路由 `select()` 进 Agent |

部署面前提（0.2.2 起新增）：`dsh-tools` 的 `ToolExecutor` 闸门缺 provider 会抛 `ToolExecutorUnavailableError`（`dsh-tools/lib/index.js:624-634`），由 `dsh-base` 插入的 `tool-executor-native` / `tool-executor-ptc` 提供（`dsh-base/cordis.patch.yml:501-505`）。自建最小 profile（含 `scripts/harness-runtime-scenarios.mjs` 拼的测试 profile）必须确认组合里有 executor，否则 23 个 `agent_teams_*` 工具一调就抛。

**审计覆盖说明**：t1 的逐包对比覆盖 38 个包，**未包含 `@deepseek-ai/dsh-agent-loop`（第 39 个）**。它是本次最关键边界所在：`lib/index.js:1000-1001` 抛出改路由错误、`:671` 在 step preparation 固定 `this.model.current()`。任何引用「0.2.2 改路由会抛错」的地方都应指到 loop，不能只指 `dsh-agent`。

## 2. 变更内容

### 2.1 0.2.2 模型选择能力探测（t8）

- `src/harness-compat.ts`：新增 `LegacySelectionRef`、`MemberSelectionChannel`、`memberSelectionChannel(agent, ref)`、`installMemberSelection(agentCtx, agent, initial)`；`HostInstallModelSelection` 用本地类型把 1 参 / 2 参两种宿主签名收敛在一处。
- `src/members.ts`：`applyRouteToSelection` 改为消费 channel；fallback 分支用 `channel.apply(transition.selection)` 记录路由，并按 `channel.redirectsInStepRetry` 决定是否声称 in-step retry。
- 未使用 `installModelSelection.length` 之类的 arity 嗅探；`scripts/verify.mjs` 与 `scripts/model-selection-compat.test.mjs` 都把「seam 只按能力分叉、源码不得出现 arity 判据」当断言。

### 2.2 失败提醒清除（t3）

- `src/members.ts`：成员失败消息补 provenance（`sourceTaskId` / `sourceAttemptId` / `sourceTaskStatus: 'failed'`），使「这条提醒属于哪一代 attempt」可从数据判定。
- `src/scheduler.ts`：新增 `failureReminderIsCurrent` / `staleFailureNotice` / `reconcileFailureReminders`；`flushDueNotices` 首行做对账，把 attempt 世代已过期的 pending notice 置 `superseded`，并把同源的 captain 未读失败提醒 discard；带 `reportKind` 的成员报告一律不动。
- 边界刻意保留：`needs_revision` / `reject` 失败、以及没有后续 attempt 的 `failed` 仍然可见——「一次失败后恢复正常」才清除，不是一刀切清空。

### 2.3 兼容矩阵（t9）

`compatibility.json:3` recommendedHost → `0.2.2-rc.1`；新增该行（无 `platforms` → 默认 ubuntu+windows）；`0.2.1-rc.5` 由 recommended 降 **preview** 但整行保留，其余 12 行未动。`engines.dsh` 仍 `>=0.1.2-alpha.2`、21 个 DSH peer 仍 `*` —— 这是刻意的：npm 对 peer 做 prerelease 检查会拒 rc 版本。

### 3.2 未解除的安装面差异（不得当作已验证）

本机无法把 0.2.2-rc.1 装进 `node_modules`：`pnpm` 不在 PATH，`npm` 因 `~/.npm` 内 root 属主文件直接 EPERM；可行入口 `npm_config_cache=/tmp/npmcache npx --yes pnpm@11`（11.28.11，已实测）只能当下载器用，真装会替换共享工作区的安装树。于是：

- 声明基线（`package.json` / overrides / lock）= `0.2.2-rc.1`；
- 实际安装树 = `0.2.1-rc.5`；
- "在 0.2.2 类型下构建并冒烟"只能在 CI 的 `pnpm install --frozen-lockfile` 环境里成立，tag 前必须有一次 CI 绿记录。

**而且要先把 §2.4 的 F5 补掉**：`verify` 链里的 `verify:capabilities`（`node --test scripts/capabilities.test.mjs`）仍在用 0.2.2 已移除的 `tools.presentAs` 与单次 `tools.execute` 形状，在装 0.2.2 的 CI 上会在这里中断。也就是说现在的本地全绿**不能**外推成「CI 会绿」——两者差的正是这一项。

## 4. 回归锁与变异证据（不以条数代替语义）

### 4.1 失败提醒的世代判别器

- 用例：`a re-failed attempt retires only the reminder of the attempt it replaced`（`scripts/member-failure-tdd.mjs:521`）。
- 变异：`src/scheduler.ts:637` / `lib/scheduler.js:459` 的 `return attemptId === undefined || task.attemptId === attemptId` → `return true`。
- 结果：22 tests / 21 pass / 1 fail，唯该用例红，`only the newest failed attempt may keep a reminder`（actual 2 / expected 1）。还原后全绿；t13 为末尾纯追加（切掉新增块后 sha256 `fede93c3f4e10c4239e703899615e921bc9c2f014920dfbfcd9edcb84eacbe93`，与 t11 锁定版本逐字节相同）。
- 评审：t14 独立复跑变异落 pass（attempt 6）。

### 4.2 0.2.2 fallback 消费判定

- 用例：`cold resume restores route and effort coherently (route-owning host, fallbackActive=false)`（`scripts/harness-compat-tdd.mjs`）。旧用例把 `{ kind: 'retry' }` 当无条件期望，正是 F2 的成因；新结构把它收窄到 ref-owning 分支，route-owning 分支换成两条更严的断言：消费判定必须 `undefined`，且 `agent.model.select` 必须收到 `{ provider: 'backup', model: 'backup-model' }`。
- 主变异：`lib/members.js:867` 恒返 `{ kind: 'retry' }` → 21 tests / 20 pass / 1 fail，报 `0.2.2 host must not claim an in-step retry`。
- 补充变异（t16 独立复核，证明断言未空转）：删 `select?.(route)` → 红在「select 必须收到 fallback 路由」；消费判定恒 `undefined` → 红在 ref-owning 分支；`redirectsInStepRetry` 恒 `false` → 4 条红，双世代分叉真的被执行。
- 评审：t16 落 pass（attempt 3）。

### 4.3 账本状态（如实）

- t6 / t11（失败提醒的两轮评审）的 verdict **绑定的是旧 revision**：`scripts/member-failure-tdd.mjs` 由 `fede93c3` 变为 `6c7e3162`（t13 追加用例），实现字节未变（`src/members.ts 1cb7aac5`、`src/scheduler.ts b2a1bcfc`、`lib/*.js` 未变，t14 已复核）。因此这两条按「revision 已被测试文件变更取代」记账，**不冒充重新验证**。
