### 1.1 engines.dsh 与 peer 范围：本次**没有**新增上限，也没有抬高下界

| 字段 | 值（未变） | 含义 |
| --- | --- | --- |

## 2. 本插件的实际改动（0.2.2 唯一硬破坏）

### 2.1 问题：成员 fallback 路由静默失效

| | 0.2.1-rc.5 | 0.2.2-rc.1 |
| --- | --- | --- |
| `installModelSelection` | `(agentCtx, selection: ModelSelectionRef)`，挂 `system-prompt/assemble` 注入 `provider`/`model` 变量 + 记录 `assembled`，再挂 `agent/request` **重写**请求配置 | `(agentCtx)`，只挂 `agent/pre-step` 追加「模型切换提示」，**不读外部 ref、不重写请求** |
| 选择存放在哪 | 调用方持有的可变 ref | 会话投影 `modelSelection`（`stateVersion: 3`，`{lastUsed, pending}`）+ `agent.model.select()` → `session.append('model/selection', …)` |
| `ModelSelectionRef` | 导出 | **删除** |

旧代码传两个实参，0.2.2 只是忽略第二个 → **不抛错**，但 `applyRouteToSelection` 写的 ref 再没人读：fallback 不生效，`agent/request-error` 的重试会再打回刚失败的主路由。TS 只在按 0.2.2 类型构建时报 `Expected 1 arguments, but got 2`，而 `devDependencies` 仍钉 rc.5，所以连编译都发现不了。

### 2.2 修复：能力探测的双通道（已落盘）

| 位置 | 内容 |
| --- | --- |
| `src/harness-compat.ts:592-601` | `LegacySelectionRef`（`{current, assembled?}`，旧路径读的那份可变引用）+ `SelectionController`（0.2.2 的宿主路由面） |
| `src/harness-compat.ts:604-615` | `MemberSelectionChannel { route(); apply(route); readonly redirectsInStepRetry }` |
| `src/harness-compat.ts:623-636` | `memberSelectionChannel(agent, ref)`：`const select = typeof controller?.select === 'function' ? controller.select.bind(controller) : undefined`；`route()` 优先读投影、回退 ref；`apply()` 恒写 ref，有 `select` 时再 `select(route)`；`redirectsInStepRetry: select === undefined` |
| `src/harness-compat.ts:656-665` | `installMemberSelection(agentCtx, agent, initial)`：`channel.redirectsInStepRetry ? install(agentCtx, ref) : install(agentCtx)` —— 旧宿主 2 参、0.2.2 只传 1 参 |
| `src/members.ts:582-587` | `applyRouteToSelection(channel, route)` 只调 `channel.apply(...)`（原实现直接改 ref） |
| `src/members.ts:986` | 成员 setup 改为 `installMemberSelection(childCtx, child, modelSelection(selection))` |
| `src/members.ts:1007` / `:1019` | fallback 分支 `applyRouteToSelection(channel, …)` / `selectFallbackRoute(channel.route(), …)` |
| `src/members.ts:1026` / `:1037` | `channel.apply(transition.selection)`；重试判定 `channel.redirectsInStepRetry ? { kind: 'retry' } : undefined` |

判据只用运行时能力：**`typeof agent.model?.select === 'function'`**。不用 `installModelSelection.length`——打包器会丢形参，且 0.2.1 在带默认参数时长度也不可信（审计 §4.1 要点 1）。

### 2.3 已知行为差异（不是缺陷，但必须写下来）

1. **0.2.2 上不能在「在途重试」里改路由**。`dsh-agent-loop` 在 step preparation 一次性用 `this.model.current()` 固定本步路由，`agent/request` 若提出不同 provider/model 会抛 `use agent.model.select() before step preparation`。所以 0.2.2 的 `agent.model.select()` 只影响**下一个 step**；`redirectsInStepRetry=false` 就是这条语义的显式建模，fallback 分支因此返回 `undefined` 而不是 `{kind:'retry'}`，避免无意义重试。
2. **不再由插件注入 prompt 变量**。0.2.2 的宿主自己提供 `systemPrompt` 变量 `provider`/`model`（`dsh-agent-loop` 内），0.2.1 由 `installModelSelection` 注入——功能不丢，来源变了。
3. **冷启动不受影响**。`agentOptions: { provider, model, reasoningEffort }` 仍是 `AgentModel.current()` 的回落来源，这段代码未改。
4. **`agent/request` 在 0.2.2 被标 `@deprecated`**（"Retained for existing listeners; do not add new listeners"），本插件在 `src/harness-compat.ts:316` 用它抛失败拒绝，0.2.2 仍生效。**这是未来版本的预定拆除点**，见第 5 节 C11。

## 3. 部署面必须补：ToolExecutor 不再是可选

**依据**：`dsh-tools@0.2.2-rc.1 lib/index.js:624-634`，`selectExecutor()` 取不到 provider 就 `throw new ToolExecutorUnavailableError()`；`dsh-base@0.2.2-rc.1 cordis.patch.yml:501-505` 第一次插入 `tool-executor-native`（`tool-executor-ptc` 默认 `disabled: true`）。

**对本插件的含义**：23 个 `agent_teams_*` 工具（`src/tools.ts` 里 23 处 `ctx.tools.register(defineTool({…}))`）都要经 executor 派发。

- 走 `dsh base` 组合的 profile：自动带上，无需改；
- **自建最小组合**（`scripts/harness-runtime-scenarios.mjs` 拼的测试 profile、`plugin-manager-install` 类用例）：必须先确认组合里有 `tool-executor-native`，否则工具一调就抛。`cordis.patch.yml` 只插 `agent-teams` 一个 entry，**不会**替 profile 补 executor——这是组合契约，不是插件能自救的东西。

这条要同步进安装前提（README / 市场条目）：**0.2.2 起「注册了工具」不等于「工具能跑」。**

### 5.2 探针流程（每次升级宿主前）

1. 解包目标版本（`npm pack` + `tar --strip-components=1`，见审计附录 A），或直接用已安装的 `node_modules`。
2. 跑 C1–C4 的符号断言：`agent.model.select` 是函数；`SESSION_FORMAT_VERSION`；`restrictableNames`；`deliverSubagentPrompt`/`followup`。
3. 跑 C7：`grep tool-executor` 目标版 `dsh-base/cordis.patch.yml`。
4. 跑 `node scripts/compatibility.mjs`（矩阵形状 + engines/peer 自洽）+ `node scripts/verify.mjs` + `node --test scripts/model-selection-compat.test.mjs`。
5. 任一条失败 → 该版本进「需要新审计」队列，**不得照抄本文结论**。

### 5.3 已知的结构性方向（推断，不是已验证事实）

0.2.2 把「调用方持有可变选择」整体换成「会话投影 + `session.append` 事件」：`ModelSelectionRef` 删除、`agent/request` 弃用、`installModelSelectionProjection` / `SessionHistoryController` / `recordSubagentModelSelection` 全部退场。方向是「插件不能再从外部改写一次请求，只能记录一个选择」。若 0.2.x 继续这个方向，下一批会动的是剩余的请求级覆写接口——首当其冲就是 C11（`agent/request` 删除）和 `AgentOptions` 的 route 语义收敛。

### 8.2 F2：冷恢复场景的过期假设（已修）

`scripts/harness-runtime-scenarios.mjs:225`（改前）在冷恢复跑之前同时禁用 `headless-startup` 与 `headless-runner`。0.2.2 的 `dsh-headless/cordis.patch.yml:28-29` 新增：

### 8.3 `ctx.tools.execute` 入参从「单次调用」变成「批次」（已由 t18 修复）

`0.2.2-audit.md` §3 曾判定「dsh-tools 的 `defineTool` / `ToolRunContext` / `restrict` 形状与报错文本一致」，**遗漏了 `ToolsService.execute` 的入参**。这次真机跑出来的事实：

- 0.2.2：`dsh-tools/lib/index.js:641-643` `async execute(input) { return this.selectExecutor(input.agent).execute(input); }` → `dsh-tool-executor-native` → `executeToolBatch(input, …)`，而 `pipeline.js:27-33` 解构的是 `const { calls: toolCalls, signal, agent, toolSet, maxParallelToolCalls } = input;` 再 `toolCalls.map(...)`；
- 老形状 `{ name, arguments, callId, agent, signal }`（`ctx.tools.execute` 单次调用）在 0.2.2 里 `calls === undefined`，直接 `TypeError: Cannot read properties of undefined (reading 'map')`，被包成 `ToolBatchExecutionError`；
- 0.2.1-rc.5 上同样代码可用（同一 fixture 在 rc.5 全绿）。

**对本插件运行时无影响**：`grep -rn 'tools\.execute(' src/` 无命中（插件只用 `defineTool({…}).execute(args, exec)` 的**工具定义**回调，不直接调 `ctx.tools.execute`）。

**对 CI 有影响**：全部 fixture 里只有两处直接派发工具——`scripts/fixtures/harness-runtime-entry.mjs:118`（1 次）与 `scripts/fixtures/harness-runtime-stability.mjs:74`（2 次），都是单次调用形状；其余 fixture（protocol / idle / web-approval）不直接调 `ctx.tools.execute`，只做工具集合与投影断言。所以 0.2.2 上实测红的是 `progressive-entry` 与 `stability`，其余场景不受这一项影响。修它需要：

1. fixture 侧按能力分叉（新形状是 `{ calls: [{ id, name, arguments }], agent, signal }`，返回值也从「单次结果」变成「批次结算」）；
2. 结果解包逻辑跟着改，且不能动 rc.5 分支的行为。

这一条在 t17 阶段是**阻塞项**（0.2.2 上「全矩阵绿」在它修完之前不可能成立），已移交 t18。

**状态：已由 t18 修复（2026-11-07）。**以上问题描述保留为历史记录。

修法（能力探测，零 arity 嗅探）——`const batchExecutor = typeof ctx.tools.setExecutor === 'function'`（`scripts/fixtures/harness-runtime-entry.mjs:128`、`scripts/fixtures/harness-runtime-stability.mjs:68`；两处上方各有一行注释说明 0.2.2 的 `ToolExecutionInput` 才是批次形状）：

- 0.2.2 分支：`execute({ calls: [{ type: 'tool-call', id, name, arguments: JSON.stringify(args) }], agent, signal })`，按 `callId` 从 `results[].result` 取回单次结果；
- rc.5 分支：保持原单次形状 `{ name, arguments, callId, agent, signal }`；
- 调用方仍拿 `ToolExecutionResult`，既有断言一条未改（无 skip、无放宽）。

证据（t18 报告，装置同 §8.6）：

| 场景 | 0.2.2-rc.1 修复前 | 0.2.2-rc.1 修复后 | 0.2.1-rc.5 修复后 |

### 8.4 F4：`agent.ctx.tools.presentAs is not a function`（已由 t19 修复）

0.2.2 上跑 `protocol-compatibility` 时报的第一处错误（`scripts/fixtures/harness-runtime-protocol.mjs:122`，旧调用点）。根因**不是改名**，是职责下移：

- 0.2.1-rc.5：`tools.presentAs('ptc')`（`dsh-tools@0.2.1-rc.5 lib/index.js:2911-2929`，类型 `index.d.ts:610`）用 per-scope `layer.mode` 把该 scope 的 presentation 折叠成 `run_code`；
- 0.2.2：整仓 `presentAs` **0 命中**、`ToolPresentationMode` 不再导出；model-facing schema 与批次执行交给 per-scope ToolExecutor —— `@deepseek-ai/dsh-tool-executor-ptc` 的插件体就是 `ctx.tools.setExecutor(new PtcExecutor(ctx, config))`（该包 `lib/index.js:1774-1776`，inject = tools/systemPrompt/ptcRuntime），而 dsh-base 默认把它 disabled（`cordis.patch.yml:504-506`），正是留给按 scope 选择性启用；选择语义见 `dsh-tools@0.2.2-rc.1 lib/index.js:598-617`（`scopeOf(this.ctx)`、每 scope 一个 executor）。

修法（只动 `scripts/fixtures/harness-runtime-protocol.mjs`，+24/-1）：新增 `presentPtc(agent)` —— `typeof tools.presentAs === 'function'` 时原样走 rc.5 的 `presentAs('ptc')`；否则断言 `typeof tools.setExecutor === 'function'`，动态 `import { PtcExecutor } from '@deepseek-ai/dsh-tool-executor-ptc'` 并 `tools.setExecutor(new PtcExecutor(agent.ctx, {}))`，随即断言 `assemble().tools` 恰为 `['run_code']`（防静默退化成 native）。调用点改为 `ptc ? await presentPtc(agent) : agent.ctx.tools.restrict({ allow: businessNames })`。`for (const ptc of [false, true])` 双分支全保留。
