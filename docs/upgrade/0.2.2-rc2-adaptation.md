# 适配 DSH 0.2.2-rc.2（AgentTeams 0.1.32）

> 本文记录 `0.2.2-rc.1 → 0.2.2-rc.2` 的实际迁移。它是对
> [0.2.2-migration.md](./0.2.2-migration.md) 与 [0.2.2-release-notes.md](./0.2.2-release-notes.md)
> 的**追加**，那两份是 rc.1 世代的历史报告，原文保留不改。

## 结论（Verdict）

**rc.1 → rc.2 不是「只换字面量」的 RC 递进 —— 它改掉了 `dsh-subagent` 的四处运行时契约，其中一处是加载期 P0：rc.2 上插件根本注册不了。** 静态审计一开始判「无源码 API 破坏」是错的，被真机探针与两代对照实验证伪。四处破坏（F12 / F14 / F13 / F15）全部修复，本机 `pnpm verify` 42 段全绿。

这个错判值得留档：`dsh-upgrade-audit` 的 npm 产物对比里，`dsh-subagent` 的顶层 `lib/index.js` export 语句从 25 → 26（只加 `ROOT_AGENT_NAME`），**零 REMOVED**。但破坏发生在 `SubagentRuntime` 类的**实例方法**和**进程稳定 symbol**上，不在顶层 export 列表里。**导出符号 diff ≠ 运行时契约 diff**；跨 RC 适配必须补一层「真机实例化探针」与「两代真机 CLI 对照」，不能只看 export 与 `.d.ts` 摘要。F15 把这条教训推到极致：连 `startActivation(spec: SubagentActivationSpec)` 的签名文本都逐字相同，变的只是 interface 的字段布局 —— 只有真机 CLI 场景能暴露。

## 2. 四处真实运行时破坏（F12 / F14 / F13 / F15）

rc.2 把成员收进**以 captain 为单一 root 的一棵 activation 树**，重写了 `SubagentRuntime`。四处破坏都不在顶层 export 里，`tsc` 只抓到其中一处（F14），其余三处是 duck-typed cast、进程稳定 symbol 与 interface 字段布局，编译期全看不见。

### F12 — 投递 symbol 移除（加载期 P0）

- **before（rc.1）**：`Symbol.for('dsh.subagent.deliverPrompt')` 是 `SubagentRuntime` 上的 function（`a/lib/index.js:3103`），签名 `(parent, childId, content, source, signal, delivery)`。插件 `src/harness-compat.ts:29/:36` 用它做 FIFO 投递与退役成员守卫。
- **after（rc.2）**：两个 symbol（`deliverPrompt`、`queuePrompt`）都消失；宿主改走 `SubagentManager.deliverPrompt(childId, content, { source, signal, delivery })`（`b/lib/index.js:1768-1787`），经 service `prompt()`（`:3197`）与 `requireManager()`（`:3264-3267`）进入。
- **影响**：`src/tools.ts:806` `installRetiredMemberGuard` 在插件**加载时**必调 `guardSubagentDelivery` → `src/harness-compat.ts:418` 抛 `unsupported('cannot install complete retired-member guard')` ⇒ 插件在 rc.2 上根本注册不了；`installContinuableMemberSetup`、`queueMemberPrompt` 同样抛。
- **修**：新增 `export function installModernDelivery(runtime)` —— 幂等，仅当 `deliverPrompt`/`followup`/`queuePrompt` 皆非 function 且 `runtime.requireManager` 是 function 时，用 `Object.defineProperty` 装上保持旧 `Deliver(parent, childId, content, source, signal, delivery)` 签名的 shim，惰性转调 `requireManager().deliverPrompt(childId, content, { source, signal, delivery })`。在 `guardSubagentDelivery` 与 `installContinuableMemberSetup` 开头各调一次。
- **为什么不用 `runtime.prompt()`**：它会 mint `source = { kind: 'user', ... }`，丢掉插件 `agentTeamsSource({ kind: 'agent-teams' })` 的持久归因。shim 保留 `parent` 让 `isRetired(sender, targetId)` 照常定位 stateDir，守卫照常 wrap/restore。manager 在 `Service.init` 的 `ctx.inject(['agents'])` 才绑定（`:2980-2998`），必须惰性 resolve。

### F14 — 公开 `list()` 移除（tsc 抓到）

- **before**：`a/lib/types/index.d.ts:300 list(): string[]`（`a/lib/index.js:3296` `return [...this.providers.keys()]`）。
- **after**：rc.2 `.d.ts` 无 `list`。`src/members.ts:1271` 直接调 `ctx.subagents.list()` ⇒ `TS2339: Property 'list' does not exist on type 'SubagentRuntime'`（`tsc -p tsconfig.json --noEmit` RC=2，全 host tsc 仅此一错）。
- **修**：新增 `export function listedProviderNames(runtime)`（`list()` if function，否则 `providers.keys()` if Map-like，否则 `[]`），`src/members.ts:1271` 改用它。rc.2 真机探针：`list` undefined、`providers` 是 Map、`providers.keys()` 返回 `[]`。

### F13 — `drainChildren` 移除（语义鸿沟，不能直接换名）

- **before（rc.1）**：`drainChildren(parent, childIds)`（`a/lib/index.js:1378-1389`）按 childId 从 `resident` Map 精确 dispose 选中的 direct children，兄弟成员保持 admitted/resident。service 包装 `a:3148-3152` manager-less 是 accepted no-op。
- **after（rc.2）**：只留 `drainDescendants(parents: readonly Agent[])`（`b/lib/types/index.d.ts:224`、impl `b/lib/index.js:1460-1469`），按 root 停**整棵树**。
- **两个调用点**：`src/tools.ts:624`（`stopTeamMemberActivations`，halt/delete team，停全队）与 `:2182`（update_member 换 LLM route 前**只停单个成员**）。`drainDescendants([captain])` 在 update_member 会误杀其它成员 ⇒ 不能换名。
- **排除的路径**：`src/scheduler.ts:1107/:1132` 的 `receipt.dispose` 只在 `result` 结算时触发，halt/update_member 手里只有 team.json 的 member id，拿不到 receipt；`interrupt`（`b:1393-1409`）保留 Activation/inbox/queued work，不是 drain（`src/tools.ts:621-622` 注释明确排除）。
- **修**：`drainMemberChildren` 加 rc.2 分支，复用 F12 已验证的 `requireManager()` duck-type：`manager.resident.get(childId)` 取选中 activation → `manager.disposeRoots(targets, 'selected activation(s)')`。这与旧 `drainChildren` 精确等价（`dispose`→`close` 同步设 `activation.closing` 关 admission、`finishDisposal(stop=true)` cancel+whenIdle+flush+`resident.delete`+`releaseSlot`+emit `subagent/end`），且只动选中项。manager 未绑定 = 无 resident = rc.1 no-op，`CONTINUATION_UNAVAILABLE` 按 best-effort 吞掉返回。legacy 分支（`drainChildren`/`drainContinuableChildren`）保持原样，双代都在。

### F15 — `SubagentActivationSpec` 从嵌套 `request` 改成拍平顶层（真机 CLI 坐实）

- **before（rc.1）**：`a/lib/types/types.d.ts:25-38` `interface SubagentActivationSpec { provider; label; childId?; request: Omit<SubagentStartRequest,'label'|'signal'>; signal; delivery }` —— `parent`/`prompt`/`cwd`/`agentOptions` 全嵌在 `spec.request.*`。`a/lib/index.js:3051-3063 startActivation(spec)` 读 `spec.request.parent.id`、`spec.request.maxDepth`、`spec.request.outputSchema`；`a:1466 submitMaterialized(..., request.prompt, ...)`。
- **after（rc.2）**：`b/lib/types/types.d.ts:23-40` `interface SubagentActivationSpec extends Omit<SubagentStartRequest,'label'|'signal'> { provider; label; name?; childId?; signal; delivery }` —— **无 `request` 字段**，`prompt`/`parent`/`signal`/`agentOptions`/`agentPreset`/`cwd`/`outputSchema`/`maxDepth` 全在顶层。`b/lib/index.js:3018-3036` 读 `spec.parent.id`（UNAUTHORIZED 校验）、`b:1557 submitMaterialized(..., spec.prompt, ...)`。两代 `lib/types/index.d.ts:136/146` 的 `startActivation(spec: SubagentActivationSpec)` 字面签名不变 ⇒ **导出符号 diff 与签名摘要都看不见**。
- **影响**：插件 `src/harness-compat.ts:126 startMember` 仍按 rc.1 形状发 `{ ...spec, request, delivery:'parent' }`，rc.2 读 `spec.parent`/`spec.prompt` 全 undefined ⇒ 初始 prompt 投不进去、parent 校验失败，成员 activation 2ms 内被拒（`lifecycle`/`fallback`/`failure`/`captain-idle-wakeup` 的 `memberRequests:0`、task pending、`state:'rejected'`）。**rc.1 对照实验**（同一 tarball 跑 rc.1）这四条全绿、memberRequests 6/7/1/5 ⇒ 坐实 F15 是 rc.2 世代问题、不是 F12/F14/F13 的回归；两代 `install.stderr.log` 逐字相同（同样 5 个 allowScripts warn）排除 npm install-scripts 环境假设。
- **修**：`startMember` 改发**双形状** `{ ...spec, ...request, request, delivery:'parent' }` —— 顶层带 `parent/prompt/cwd/agentOptions` 供 rc.2 读，嵌套 `request`（已剥 persona/toolFilter）供 rc.1 与 `guardSubagentCreation`（`src/harness-compat.ts:153` 读 `args[0].request.parent`）照常工作；`CreationBoundary.startActivation` 类型放宽为 union。rc.2 路径无 `Object.keys(spec)` 严格形状校验，多余 `request` 键被忽略（`b:2312-2330`）。一条代码路径服务两代、零世代探测、rc.1 零回归。
- **测试**：`scripts/harness-compat-tdd.mjs` 新增 `'0.2.2-rc.2 flat activation spec exposes top-level task fields and keeps the guarded request'`，断言顶层字段存在、persona/toolFilter 不泄漏、嵌套 `request` 与守卫 parent 保持。

## 4. 回滚

本分支 `codex/dsh-0.2.2-rc2` 的改动分为可独立回退的两组：声明面（cohort/版本/矩阵/lockfile/workspace）与四处源码修复（`src/harness-compat.ts`、`src/members.ts` + 对应测试）。回退声明面前需连同 `lib/` 与 `lib/git-artifact-stamp.json` 一起重建，否则 `git-artifacts` 闸门红。回退到 rc.1 宿主时，F12/F13 的 modern 分支因 `requireManager`/symbol 判定不命中而自动走 legacy 路径，F15 的双形状 spec 在 rc.1 上顶层字段被忽略、仍读嵌套 `request`，双代兼容设计不要求二选一。
